### Pi のシステムプロンプトの構成

`system-prompt.ts` は、プロンプトを1つの文章ではなく、名前付きの節（section）に分けて組み立てている。各節は `<tools>` のような XML タグで囲まれる。

| 節 | 内容 |
|---|---|
| preamble | 「pi という coding agent harness の中で動くコーディングアシスタント。ファイルの確認、コマンドの実行、コードの修正を手伝う」の1文 |
| tools | 使えるツールの名前と1行の説明の一覧（既定は read・bash・edit・write） |
| rules | 守るルールの箇条書き。ツールの種類によって増減する |
| docs | Pi 自身のドキュメントの場所。「利用者が Pi 自体について聞いたときだけ読む」と条件が付いている |
| project_context | 利用者が置いたプロジェクト固有の指示ファイルの中身 |
| skills | 使えるスキルの一覧 |
| cwd | 作業ディレクトリ |

### 自分の INSTRUCTIONS との比較

| 観点 | Pi | 自分の INSTRUCTIONS |
|---|---|---|
| 役割 | 1文（コーディングアシスタント） | 1文（AIE2026 の学習支援エージェント） |
| 長さ | 固定の文は短い。状況に応じて節が増える | 5項目の箇条書き1つ |
| ツールの使い方 | 使うツールに応じてルールが変わる（例：grep・find・ls が無く bash があるときだけ「ファイル操作には bash を使う」を足す） | ツール名を指示文に直接書く（search_glossary、get_lecture_summary） |
| 回答の形 | 「簡潔に答える」「ファイルパスを明示する」の2つだけ | 「最後に関係する回を示す」など、形式を細かく指定 |
| 知らないことへの対応 | 書かれていない | 「用語集にないことは推測で断定せず、ないと伝える」 |
| 利用者への配慮 | 書かれていない | 「宿題の答えそのものは書かず、ヒントで導く」 |
| 利用者が足せる指示 | 足せる（project_context、appendSystemPrompt、skills） | 足せない（固定の文字列） |
| 環境の情報 | 作業ディレクトリを渡す | 渡さない |

### 書かれていないもの

- **Pi に書かれていないもの**：知らないことを推測で答えない指示、答えを教えすぎない指示。コーディングエージェントでは、これらは利用者のプロジェクトごとに違うので、固定の文に書かず、利用者が足す仕組み（project_context など）にしている。
- **自分の INSTRUCTIONS に書かれていないもの**：状況に応じてルールを変える仕組み、利用者が指示を足す仕組み、実行環境の情報。学習支援という1つの用途に絞っているので、固定の文で足りている。
- **確認できなかったこと**：各ツールの説明（`toolSnippets`）とルール（`toolGuidelines`）は、このファイルでは外から渡される値で、実際の文面は別のファイルにある。そのため、Pi が実際にモデルへ渡す全文は、この比較では確かめていない。

### Pi を実際に動かした結果

Pi に「このリポジトリの `app/agent.py` を説明して」と1回だけ聞いた。

- Pi は、まず `read /workspaces/lecture-ai-engineering-2026/app/agent.py` を呼び、ファイルを読んでから説明した。
- 回答は、`INSTRUCTIONS`、通常のエージェント、MCP 版、補助関数、`main()` の順に整理されていて、使用例のコマンドも付いていた。
- 自分のエージェントなら最初に `search_glossary` を呼ぶ場面で、Pi は `read` を呼んだ。使うツールが、システムプロンプトの `tools` 節（既定は read・bash・edit・write）で決まっているためだと考えられる。
- Pi は、`INSTRUCTIONS` の「回の内容を聞かれたら」の「第N回」が欠けているように見える、と指摘した。実際のコードは「回の内容を聞かれたら get_lecture_summary を使う」で、欠けているわけではない。モデルが読み違えた可能性がある。
- 回答の最後に「関係する回（第N回）」は付かなかった。これは自分の `INSTRUCTIONS` の指示で、Pi には無いので、予想どおりの結果だった。

実行は1回だけで、モデルも自分のエージェント（Gemini）とは別（Claude）なので、ふるまいの違いがシステムプロンプトだけによるとは言えない。

- 気づき・疑問：
  - 自分の `INSTRUCTIONS` は、禁止や条件（「必ず確認する」「断定しない」「答えは書かない」）が中心だった。Pi のルールは、使うツールに合わせて「何を使うか」を決める内容が中心で、禁止は少ない。
  - 1つの用途に絞ったエージェントは固定の文でよく、利用者や環境ごとに変わるエージェントは、節に分けて差し替えられる形が向いていると考えた。
  - Pi は、ファイルを読む `read` を自分で呼んで説明を作った。ソースを読んだだけでなく、実際の挙動でも、ツールの組が違うと最初の動きが変わることが確かめられた。
  - モデルが、コードを読み違えて「欠けている」と指摘した。エージェントの回答は、そのまま信じず、元のコードで確かめる必要がある。
  - 次に確かめたいこと：`project_context` に指示を置いたときに、Pi の回答がどう変わるか。
